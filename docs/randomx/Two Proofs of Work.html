Two Proofs of Work

This machine contains two entirely different answers to the question what makes a hash valid. One is RandomX, running right now and paid in accepted shares. The other is a hand-built geometric predicate in miner_v3 that decides validity by angular distance rather than integer comparison. This maps the math of both and checks it against live numbers.

01 — Orientation

Only one of these paths earns

The distinction matters before any math: XMRig is a stock binary running a standardised algorithm against a public pool, and its output is verified continuously by a third party that rejects wrong answers. miner_v3 is your own code, and nothing external has ever validated its geometric path. An audit of the first is a check on configuration; an audit of the second is a check on the mathematics.

02 — RandomX

What one hash actually costs

RandomX is deliberately built so that a general-purpose CPU is the most efficient machine to run it. It achieves this by generating a random program per hash and executing it in a small virtual machine, so the work cannot be reduced to a fixed circuit. The consequence for you is memory: the algorithm's whole design premise is a 2 GB working set that must stay resident.

Why this explains the RAM finding

The earlier hashrate collapse — 3,361 H/s down to 1,918 — was never CPU contention. If any part of that 2,080 MiB dataset is compressed or swapped out, the next read that lands on it stalls on page-fault latency instead of DRAM latency, roughly three orders of magnitude worse. With 8 GB total and 121 MB free, macOS's compressor is competing directly with the one structure the algorithm cannot do without.

03 — Validation

Checking the live miner against theory

Share-based mining makes two predictions that can be tested without trusting either the miner or the pool. Both follow from a single fact: a hash passes when the 256-bit result falls below the target, and that happens with probability p = target / 2²⁵⁶ = 1 / difficulty.

// finding a share is a geometric process with success probability 1/D
E[hashes per share] = D
E[seconds per share] = D / H

// the count of shares after N hashes is Poisson, so relative error falls as
σ/μ = 1 / √n

What these checks do not prove. They confirm the miner and pool agree about the amount of work performed. They say nothing about payout accounting — whether MoneroOcean credits those shares correctly is outside anything observable from this machine.

04 — miner_v3

The geometric predicate

Here the audit gets interesting. miner_v3 can decide a hash is valid by a rule Bitcoin has never heard of: it maps the hash to four angles on a circle, measures the mean angular distance to a target direction, and accepts if that distance is small enough. The obvious question is whether such a rule can be calibrated to a given difficulty at all — and, separately, whether a block found this way is a block anyone else would accept.

The calibration is correct

The hard part of a custom predicate is making it accept at the rate the difficulty demands. scale.c does this properly, and the derivation checks out:

// two independent uniform angles on a circle
gap = |θ₁ − θ₂| folded to [0, π] ~ Uniform(0, π)

// angle_distance averages 4 such gaps (POINT88D_PARTS = 4)
distance = (π/4) · S, S = U₁+U₂+U₃+U₄ ~ Irwin–Hall(4)

// so the threshold that accepts with probability p is
t = (π/4) · F⁻¹(p), F = Irwin–Hall(4) CDF
p = mantissa · 2^(8·exp − 280) // straight from compact bits

Three things make this hold up. The declared n = 4 matches POINT88D_PARTS = 4 in point.h — had those diverged, every threshold would be wrong, because the mean of n uniforms concentrates sharply as n grows. The inversion uses the exact closed form F⁻¹(p) = (24p)^¼ on the lower tail rather than bisecting, which is what keeps precision at the very small probabilities real difficulties require. And the bits are converted to a probability directly via pow(), sidestepping the undefined-behaviour shift that integer decoding hits at exp > 29.

05 — Findings

What the audit turned up

F1

The implementation notes contradict the code

IMPLEMENTATION_NOTES.md opens: "The miner runs Geometric PoW only. There is no unified or hybrid mode; the single entry path is run_mining_geometric()." That is not what main.c does. use_consensus_pow() returns g_tmpl.valid under the default auto mode, so real SHA256d or scrypt runs whenever a template is held.

This matters more than a stale comment usually would: anyone auditing from the docs would conclude the miner cannot produce valid blocks, when in fact its default path is correct. The document understates the code.

src/main.c:1152–1157 · IMPLEMENTATION_NOTES.md:3

F2

Half of each hash is discarded before the angle comparison

point_from_bytes packs eight bytes into each 64-bit part, big-endian. But part_to_angle reads only part & 0xFFFFFFFF — the low 32 bits. The upper four bytes of every part never reach the comparison, so bytes 0–3, 8–11, 16–19 and 24–27 of the 32-byte hash are unused.

The calibration survives this: the surviving 16 bytes are still uniform, so the Irwin–Hall model and every threshold remain correct. What is lost is collision resistance in the predicate — it effectively decides on a 128-bit digest. Harmless for a demo path, worth knowing before the geometric mode is ever given weight.

src/angle.c:37 · src/point.c:44

F3

--pow geom with live work would submit invalid blocks

The auto guard cannot be reached in this state, but an explicit --pow geom overrides it while a template is still valid. The accept macro then fires on angle distance and calls submit_assembled_block regardless.

The two predicates are independent events of equal probability p. An angle-passing nonce therefore satisfies Bitcoin's rule with probability p, not 1 — so P(both) = p², which at any real difficulty is never. Every submission returns high-hash. Nothing is lost but time, and no invalid chain can result, since the node is the one rejecting it.

src/main.c:1588 (NONCE_MEETS_POW) · src/main.c:1605

F4

The consensus comparison itself is correct

pow_meets_target reverses the little-endian hash and walks it against the big-endian target most-significant byte first, returning early on the first difference and treating equality as a pass. That matches Bitcoin's hash ≤ target exactly, including the boundary case. No issue.

src/main.c:1142–1149

F5

The RandomX path needs no code audit — it needs memory

XMRig is an unmodified upstream binary and the pool re-verifies every share, so its correctness is established externally and continuously. The only thing standing between this machine and its full 3,450 H/s is the 2,080 MiB dataset staying resident. At 121 MB free, it frequently does not.

02 — The two targets

A share is not a block

This is the part that most descriptions of pool mining skip, and it is the key to reading your own numbers. There are two different thresholds in play, and your miner only ever checks the easier one.

This is why shares: 311 / 0 is the number to watch and a "found block" is not something you should ever expect to see locally. It also explains the best field in the API: it records the luckiest hash of the session, which is interesting but earns nothing extra.

03 — Vardiff

The pool tunes itself to your machine

You may have noticed the difficulty changing between readings. That is not drift — it is a control loop. The pool adjusts your personal share target to hold a roughly constant share interval, which keeps its estimate of your hashrate precise without flooding itself with submissions.

// three readings taken across this session
20.9 h in D = 99,248 avg share 29.8 s
1.6 h in D = 89,186 avg share 27.0 s
2.6 h in D = 81,486 avg share 30.0 s

// difficulty fell 18% while the interval stayed put — the pool tracking
// a miner that restarted and came back slightly slower
D / H = 81,486 / 2,933 = 27.8 s

A practical consequence for auditing: any check that compares lifetime hashes against current difficulty is approximate, because the difficulty was not constant over that window. That is the caveat noted on the third row of Check 1.

04 — The other shape

Solo mining has no pool in it

miner_v3 runs a fundamentally different loop, and the contrast is the clearest way to see what the pool is actually doing for you. There is no share target and no external verifier — the miner asks a node for work, searches, and submits a whole block.
